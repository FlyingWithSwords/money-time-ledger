## 1. 一句话定位与差异点

> **把每一笔支出换算成"我还需要工作多久"，让省钱有痛感、有依据、不靠意志力。**

不是记账本，是**消费痛感仪表盘**。记账只是采集，价值在"看见代价"。

| 维度 | 随手记 / 网易有钱等通用记账 | 本产品 |
|---|---|---|
| 核心问题 | "我的账记全了吗" | "这笔钱值不值我花掉的那些小时" |
| 主视角 | 分类占比、预算超支 | 时间成本 + 情绪成本 |
| 对比对象 | 预算、他人均值、行业平均 | **只和用户自己的历史比**（隐私红线） |
| 收入角色 | 顶部一个数字 | 换算真实时薪的锚点（接单 856 元 = 18 小时编码） |
| 数据来源 | 手动为主 | 官方账单文件导入为主、手动为辅（412 行旧账必须能一次迁入） |
| 数据归属 | 云账户 | 本机存储，无账户体系 |
| 输出物 | 报表 | 月度复盘卡片（可分享，默认隐藏金额） |

**不做的事**（防范围膨胀）：多人/家庭共享账本、信用卡还款提醒、理财推荐导购、社区。
## 2. 用户画像与核心场景

**画像**：22 岁，大四 / 实习期；零星接单收入（56–856 元/单，写 html/js/SpringBoot/vue 页面）、实习工资约 2200–2600 元/月、偶尔津贴；日常靠花呗 + 美团，单笔午餐 12–18 元；会为一笔 0.04 元的单车优惠单独记一行。对"分类错、金额差一分"极度敏感。

| # | 场景故事 |
|---|---|
| S1 | 月底打开旧 Excel 想算这个月花了多少，"三餐总计"因 8 月只 SUM 了一笔而对不上，手工核 359 行花 40 分钟，最后发现 4 月还差 120 元。→ 他要**导入后自动对平、差一分就报警**的工具。 |
| S2 | 中午点 15 元外卖没感觉。晚上看到"本月餐饮 1180 元 ≈ 你工作 25.6 小时"，突然意识到相当于白干三天半。→ 他要**痛感即时可见**，不是月底才知道。 |
| S3 | 基金放着 2000 块，每天涨跌三五块，不知道赚没赚、也不知这笔算不算自己的钱；想换手机时翻去年同月账单，发现"花了 4300，其中 1900 是冲动消费"。→ 他要**持仓并入净资产**，且**只用自己的历史当镜子**。 |
## 3. 信息架构（移动端底部 5 Tab + 抽屉页）

| # | 页面 | 一句话职责 | 核心元素 |
|---|---|---|---|
| P1 | **总览**（Tab1） | 3 秒回答"我现在有多少钱、这个月危不危险" | 净资产（现金+基金−负债）、本月支出/收入/结余、时间成本条、与上月差值、近 6 月支出迷你柱图、待处理提醒（待分类笔数 / 疑似重复 / 复盘卡已生成） |
| P2 | **流水**（Tab2） | 逐笔账的检索、修正、补录 | 按日分组列表（日期 + 当日合计）、行内：分类图标 / 金额 / 渠道 / 时间成本小字 / 标记圆点、搜索、筛选（时间·分类·渠道·金额区间·标记）、左滑编辑·右滑标"最不值"、FAB 快速记账 |
| P3 | **导入**（Tab3，兼空状态入口） | 把外部数据安全地搬进来 | 三入口卡片（官方账单文件 / 截图识别 / 旧表格迁移）、导入历史（来源·笔数·成功失败·时间）、**对账结果页**（明细合计 vs 文件合计）、字段映射预览 |
| P4 | **基金**（Tab4） | 持仓与收益，并入总资产 | 持仓列表（代码/名称/份额/成本价/现价/市值/持有收益/收益率）、总市值与总收益、收益曲线（日/月/年）、净值时间戳与"数据可能延迟"提示、手动刷新 |
| P5 | **洞察**（Tab5） | 用数据说"该不该省、省哪里" | 分类占比（环形）、支出趋势（折线）、时间成本榜（本月最贵 5 笔）、冲动消费统计、月度复盘卡片列表、对比视图（vs 上月 / vs 去年同月 / vs 近 3 月均值） |
| P6 | 设置与分类（抽屉） | 口径、隐私开关、分类维护 | 时薪口径与月工时、目标设定、导出·加密备份·恢复、清空数据、隐私说明；一/二级分类增删改、关键词自动归类规则（可见可编辑）、合并分类 |

**导航原则**：底部 5 Tab 固定；P6 从总览右上角进入；任何页面不出现"登录"。
## 4. 核心机制设计（"让用户知道钱来之不易"怎么落地）

| 机制 | 触发条件 | 呈现方式 | 边界 |
|---|---|---|---|
| **M1 劳动时间换算** | 单笔 ≥ 阈值（默认 100 元）录入后即时出现；月度复盘全量计算；流水列表常驻 | 金额下方灰字 `15.00 ≈ 0.33 小时`；≥8 小时升级为"天"；总览横条 `本月支出 ≈ 26.4 个工作日`。时薪三档：①月薪÷月工时（默认 8000÷174≈46 元/h）②直填时薪 ③**真实时薪**=接单收入÷填报工时（近 3 笔均值） | 只做参照，不做"你真浪费"式评判；阈值与口径可关闭 |
| **M3 月度复盘卡片** | 每月 1 日首次打开 App 自动生成上月卡片（纯本地计算，无需后台）；也可手动生成 | 竖版卡片逐屏滑：支出/收入/结余 → Top3 分类占比 → 最贵一笔 → 你标记的"最不值" → 冲动消费合计 → 与上月对比（金额/百分比/箭头）→ 存下多少与目标进度 → 一句时间成本。**分享图默认隐藏绝对金额** | 超支用中性色不用红字恐吓；建议必须具体（"本周少 2 次外卖 ≈ 追平 80 元"） |
| **M4 储蓄目标与进度** | 用户设定目标（名称 + 金额 + 日期，如"换手机 3000 元 / 12 月底"） | 进度条 + `按当前速度还需 X 天` 或 `落后 Y 元`，数据 = 累计结余增量；达成时庆祝动画 + "这 3000 元 = 你 65 小时接单"；落后给一个可执行的最小动作 | 不做打卡、不做惩罚、不推送焦虑文案 |
| **M5 时间轴对比基准** | 每月 1 日（环比）；有 ≥12 月数据时（同比）；常驻（近 3 月均值参考线） | 总览 chip `比上月少花 320 元 ↓`；洞察页"去年这个月你花了 X"；分类卡右上参考线 | **只和自己比**；任何"同龄人/同城/平均用户"对比在产品内不得出现 |

**M2 冲动 / 后悔度标记（自动，无需用户操作）**

| 规则 | 触发条件 | 呈现 |
|---|---|---|
| 深夜消费 | 本地时间 23:00–05:00 的支出 | 行首紫点 + 标签「深夜」 |
| 高频小额 | 同二级分类 30 分钟内 ≥3 笔，或单笔 <10 元且同日 ≥5 笔 | 标签「碎钞」 |
| 异常单笔 | 单笔 ≥ 当月日均支出 ×3 | 标签「大额」 |
| 连续同类 | 同一二级分类连续 7 天出现（如每天一杯饮料） | 标签「习惯性」 |
| 主观 + 汇总 | 用户勾选"最不值"；每月自动统计 | 标签「后悔」；洞察页卡片 `本月被标记 X 笔，合计 Y 元，占支出 Z%` + 一句可选建议 |
## 5. 数据字段需求（给架构师的输入，非表结构）

| 字段 | 为什么必须有 |
|---|---|
| `amount`（**整数「分」**） | 旧表有 0.04 元、0.00 元、9400 元并存；浮点会漂移，必须整数分存储、显示转元固定 2 位 |
| `direction`（支出/收入/退款冲正/转账） | 旧表靠"分两张表"表达方向，导致"结算收入 vs 基础收入"差 348.13 元无法解释；退款用"公式 −12.49"实现，不可查询 |
| `occurred_at`（完整日期 + 时间） | 旧表日期是文本 `2日` 且**无年份**、同日多笔靠向下填充；导入账单需保留时分（M2 深夜规则依赖时间） |
| `category_l1` / `category_l2` | 旧表 139 个自由文本、零分类；分类是复盘唯一聚合维度 |
| `payment_channel` | 旧表把「花呗/美团/花呗优惠/拼多多」塞进"备注"，226 笔有值 134 笔空；渠道决定"这钱是不是已还" |
| `account`（花呗/余额/银行卡/现金） | 区分"消费发生"与"资金流出"；决定净资产口径（花呗未还属负债） |
| `external_id` + `source` + `imported_at` | 旧表无流水号，同日同额两笔无法区分；没有这三项无法做到**导入幂等** |
| `note` + `flag` + `manual_edited` | 备注仅展示、**不参与任何计算**；M2 标记需持久化才能被复盘引用；人工修正的值不被后续导入覆盖 |

**七个当前缺失项的处理要求**

| 缺失项 | 处理要求 |
|---|---|
| `direction` | 四值枚举；退款为独立方向（**不写成负数**），保证支出统计不被退款污染、退款可单独查询 |
| `category` | 强制二级；一级 10 个固定（见 §6），二级从固定清单选；未识别进"其他/待分类"并要求一次性归位 |
| `payment_channel` | 枚举且可扩展；导入时从原文解析，失败置「未知」并在结果页列出待确认条数 |
| `account` | 必须能表达负债账户（花呗/信用卡），否则净资产算错；同一渠道可绑默认账户减少录入 |
| `external_id` | 由「平台+交易单号」或「金额+时间+商户+序号」哈希生成；**重复不得静默丢弃，必须列出让用户决定** |
| `source` | 枚举：`wechat / alipay / bank / ocr / manual / legacy_xlsx`，用于统计各来源准确率 |
| `amount` 精度 | 整数分；汇总一律转分求和后再转元；**任何一处出现两位小数四舍五入即视为缺陷** |

**旧表 6 缺陷 → 新方案映射（用于验收）**

| 旧表缺陷 | 新方案 | 验收 |
|---|---|---|
| ① 无主键，去重无依据 | `external_id` + 幂等导入 | 同一文件导入两次，笔数不变 |
| ② 类别/账户/方向缺失或混装 | 三字段独立枚举 | 任一页面可按三维交叉筛选 |
| ③ 日期为文本、无年份、靠下填 | 真实日期时间 | 跨年数据正确归月 |
| ④ 汇总行与明细混排 | 汇总**只计算不存储** | 数据中不存在"月小计"类行 |
| ⑤ 汇总为手填常量，差 120 元 | 实时计算 + 对账页 | 导入 359 笔后明细合计与月汇总零差异 |
| ⑥ 缺 source/external_id/imported_at | 三字段必备 | 每笔可追溯来源文件与导入时间 |
## 6. 分类体系（一级 10 个 + 二级固定清单）

| 一级 | 二级（示例，6–10 项/类） | 该用户高频项 |
|---|---|---|
| 餐饮 | 早餐 / **午餐** / 晚餐 / 夜宵 / 外卖配送费 / 饮料咖啡 / 零食 / 聚餐 / 买菜 | 午餐 98 次、晚餐 39 次 |
| 交通 | 地铁 / 公交 / 共享单车 / 打车 / 火车机票 / 停车 | 地铁 12、公交 12、青桔 10、哈啰 6 |
| 居住 | 房租 / 水电燃气 / 物业 / 家居用品 / 维修 | 房租 |
| 通讯 | 话费 / 流量 / 宽带 / 会员订阅 | 话费 |
| 购物 | 数码 / 服饰 / 日用百货 / 美妆个护 / 快递运费 / 其他购物 | 拼多多 2 笔、快递 |
| 医疗 | 门诊 / 药品 / 体检 / 牙科 | — |
| 学习 | 书籍 / 课程 / 考试报名 / 软件工具 / 打印 | — |
| 娱乐 | 游戏 / 影视 / 演出 / 旅行 / 运动健身 | — |
| 人情 | 红包 / 礼物 / 请客 / 随礼 | — |
| 其他 | 手续费 / 罚款 / 待分类 / 未识别 | 5 笔金额为 0 的怪账 |

**收入侧一级**：接单报酬 / 实习工资 / 津贴补贴 / 二手转卖 / 押金退还 / 投资收益 / 其他。旧表"结算收入 vs 基础收入"差 348.13 元的根因是"转卖/押金/退费算不算收入"没有定义 —— 本产品**明确定义**：二手转卖计入收入；押金退还与退费记为 `退款冲正`，**不计收入**。

**"午餐 12 元"这类高频小额怎么归（不做成 139 个自由文本）**

1. **时间默认规则**：11:00–14:00 且 ≤50 元 → `餐饮/午餐`；17:00–21:00 且 ≤80 元 → `餐饮/晚餐`。
2. **关键词规则**（可见可编辑）：命中"美团/饿了么/外卖"→ 餐饮，按时间落午/晚餐；"青桔/哈啰/单车"→ 交通/共享单车；"地铁/公交"→ 交通对应二级。
3. **学习行为**：用户手动改过一次"美团 → 餐饮/午餐"后，同类规则**自动记住**，下次同商户直接套用。
4. **兜底**：仍无法判定 → `其他/待分类`，总览显示"N 笔待分类"；**未清零前分类占比图带"含待分类"水印**，避免被错误数据误导。
5. **禁止**：不允许自由文本分类直接入账；二级缺失自动落到该一级的"其他"。
## 7. 账单导入的产品方案（三条路径按优先级排序）

| 序 | 路径 | 定位 | 用户操作步骤 | 准确率预期 | 失败兜底 | 隐私影响 |
|---|---|---|---|---|---|---|
| **A** | **官方导出账单文件导入** | 主路径（P0），一次补齐 1–12 月历史 | ①在微信/支付宝的「账单」页内找到导出/下载账单入口（**具体菜单名需用户核实**，各版本不同，通常是账单页→常见问题/更多→下载账单，或申请交易流水证明，结果发邮箱）②邮箱下载 zip/csv（可能带密码，通常为身份证后 6 位或手机号后 4 位，**需用户核实**）③在 P3 选文件 → 本地解析 → 预览字段映射 → 确认导入 | 结构化字段解析 **95%+**；分类识别 70–85%（靠关键词规则） | 解析失败给"格式不符"清单（缺哪列）；重复项列出由用户勾选；金额不一致进对账页高亮 | **文件全程本地解析，不上传**；不索取账号密码 |
| **C** | **手动快速记账** | 日常高频（P0），最准 | FAB → 输金额 → 点分类图标（记住上次分类）→ 可选备注 → 保存 | **100%**（用户输入） | 无失败概念；离线可用 | 完全本地 |
| **B** | **截图 OCR 识别** | 补充（P1），客户点名要，但无法保证准确与幂等 | ①截图微信/支付宝账单列表 ②选图（可多选）③**设备本地 OCR** ④结果进"待确认列表"逐条核对 ⑤确认入库 | 金额 **85–92%**、日期 80%+、商户 70%、分类 60% | 不确定字段高亮待填；**不自动入库，必须人工确认**；识别失败可转路径 C 手输 | 默认**本地 OCR，图片不出设备**；"云端高精度识别"为 P2，需显式点击 + 明确告知 + 24h 删除 |

**排序理由**：A 能一次性解决"412 行旧账 + 12 个月历史"的冷启动，且天然带 `external_id` 可幂等；C 是每天真正会做的动作，必须最顺；B 体验最讨喜但准确率与去重都不可控，先做 B 会得到一个"看着能用但账永远对不平"的产品——那正是旧 Excel 的病。

**三条路径共同要求**：①结果页必须显示 `成功 N / 重复 M / 失败 K / 合计 X 元`，并与源文件合计**自动对账**，差异非 0 红色高亮 + 逐笔定位；②每次导入写 `source` 与 `imported_at`，支持"按来源撤销本次导入"；③文件/图片用后立即从内存释放，不写相册、不写临时公共目录。
## 8. 基金模块需求

| 项 | 要求 |
|---|---|
| 持仓录入 | 手动：基金代码（6 位）+ 份额 + 成本价（或总成本）+ 买入日期；多笔加仓合并为加权成本；支持清仓（记录保留，计入历史收益） |
| 实时估值 | 交易时段（工作日 09:30–11:30 / 13:00–15:00）显示盘中估值；非交易时段显示最近净值 + **明确净值日期**；估值必须带"估"字角标，与净值视觉区分，避免误当成交价 |
| 数据从哪来 | **公开净值/估值数据**（基金公司或公开财经站点的公开页面）；**不接券商/基金账户授权、不做 OAuth、不代下单**。公开数据不可用时 → 降级为**纯手动填净值**，功能不缺失 |
| 收益曲线 | 日/月/年切换；展示持有收益与累计收益率；旧表"月投资收益率"分母=累计利润+贷款债务，本产品改为**累计投入成本**，并在设置页公式可见 |
| 与总资产合并 | 净资产 = 现金类账户余额 + 基金市值 − 负债账户（花呗等未还）；市值取"最近一次成功获取的价格"，数字旁标注价格时间 |
| 断网降级 | ①用本地缓存价计算市值 + 灰色"数据截至 X 日"标签 ②基金页全部只读可用 ③恢复网络后刷新一次 ④**绝不显示 0 或空值代替**，避免用户误判资产归零 |
## 9. 隐私与资金安全边界（客户列为最重要）

| # | 红线 | 具体含义 |
|---|---|---|
| **R1** | **交易数据不上传服务器** | 无账号体系、无云端同步、无行为上报；账目与持仓仅存本机；跨设备只能通过用户自导出的**加密备份文件**迁移 |
| **R2** | **不索取任何支付凭证** | 永不要求支付账号、登录密码、支付密码、短信验证码、身份证、卡号；产品内**不存在**转账、代扣、绑卡、还款入口 |
| **R3** | **截图与图片优先在设备本地处理** | OCR 默认本地执行，图片不上传、不落公共目录；若未来提供云端识别，必须默认关闭、显式点击、明确告知且 24 小时内删除 |

**可验证的验收方式**

| 验证项 | 方法 | 通过标准 |
|---|---|---|
| R1 数据不出站 | 完成一轮完整使用（导入/记账/看洞察/加基金）后在浏览器或系统网络面板抓包 | 除基金公开行情请求外**无任何携带账目信息的请求**；行情请求不含份额、成本、金额 |
| R1 本地存储 + 备份可控 | 检查存储位置；导出再导入 | 数据仅存于应用本地，清除后确实消失（证明无云备份）；备份为加密文件、口令错误无法打开 |
| R2 无凭证入口 | 全站检查表单字段与文案 | 无"密码/验证码/卡号/身份证"输入框，无绑定账户流程 |
| R3 OCR 本地 + 图片去向 | **断网**后使用截图识别；检查上传流量与文件系统 | 断网状态下 OCR 仍可用；无图片上传请求、无副本残留 |
| 离线可用 | 全程飞行模式 | 除基金估值外，记账/流水/洞察/复盘全部可用 |
## 10. 需求池（P0 = 一个人能真正用起来的最小闭环）

| 需求 | 优先级 | 理由 | 验收标准 |
|---|---|---|---|
| 单机本地存储 + 无账号启动 | P0 | 一切体验前提，也是 R1 的落地方式 | 首次打开 10 秒内可记第一笔，无注册流程 |
| 手动快速记账（3 秒/笔） | P0 | 每天真正会做的动作 | 金额→分类→保存 ≤3 次点击；记住上次分类 |

| 完整字段模型（含 7 个缺失项、amount 用分） | P0 | 旧表 6 缺陷的根治点 | 三维交叉筛选可用；0.04 元与 9400 元同时正确显示 |
| 一/二级分类树 + 关键词自动归类规则 | P0 | "139 个自由文本"必须被消灭 | 导入后待分类占比 <20%，且可一键批量归位 |
| 官方账单文件导入 + 幂等去重 + 对账页 | P0 | 冷启动唯一可行路径 | 导入 359 笔后明细合计与月汇总零差异；重复导入笔数不变 |

| 时间成本换算（M1） | P0 | 产品灵魂，缺了就不是这个产品 | 未设时薪时引导一次；≥100 元支出显示小时数 |

| 分类占比 + 支出趋势图 | P0 | 客户需求第 3 条的最小满足 | 环形图 + 月度折线；含"待分类"水印逻辑 |
| 基金持仓手动录入 + 收益曲线 + 并入净资产 | P1 | 客户需求第 2 条 | 市值与收益率正确；断网显示"数据截至 X 日"而非 0 |

| 多币种 | P2 | 学生用户暂无需求 | 仅 1 主币种，外币只记备注 |
## 11. UI 设计要点

**移动端优先原则**：①主操作在屏幕下 1/3，Tab 固定底部，不用汉堡菜单；②数字即主角，核心金额字号最大（≥32px 等效），辅助信息降级为灰色小字；③一屏一个结论，总览不得出现需用户自己算的数字；④空状态即引导（直接给"导入账单 / 记第一笔"）；⑤必须支持深色模式（用户会深夜记账，与 M2 呼应）；⑥金额在系统字号放大 200% 时不破版，颜色不作为唯一信息载体（标记同时给文字标签）。

## 12. 待确认问题

| # | 问题 | 建议默认值 |
|---|---|---|
| Q1 | 时薪口径默认用哪个？ | 月薪 8000 ÷ 月工时 174 ≈ 46 元/h，首启 30 秒确认，可跳过 |
| Q2 | 是否保留"贷款/债务"概念？ | 保留，仅用于花呗类负债账户抵扣净资产；不做还款计划、不算利息 |
| Q3 | 基金数据用公开接口还是纯手动？ | 公开净值优先 + 手动兜底；接口不可用时纯手动仍完整可用（不阻塞 P1） |
| Q4 | 退款 / 押金退还的记账口径？ | 一律记为"退款冲正"（冲减原分类），不计入收入；二手转卖计入收入 |
| Q5 | 旧 xlsx 迁移是否必须解析公式？ | 只读**计算结果值**，不解析公式；汇总行按"月份分隔行"识别后跳过 |
| Q6 | 截图 OCR 是否上线云端增强？ | 暂不（P2），默认仅本地；上线需二次确认 + 24h 删除 |
| Q7 | 是否需要多用户 / 家庭共享？ | 不做。单机单用户，明确写入隐私说明 |
| Q8 | 微信/支付宝导出账单的菜单路径与 zip 密码规则？ | **需用户核实**（各版本不同）；文案只写"请在账单页查找导出/下载账单入口"，不硬编码菜单名 |
| Q9 | 平板/桌面是独立 App 还是同一响应式页面？ | 同一响应式实现；桌面/平板双栏，手机底部 Tab |
| Q10 | 备份口令由谁定、忘了怎么办？ | 用户自设，**不提供找回**（无服务器），必须在备份页明确告知 |
